## Memory tier protocol (agentic-memory-stack)

When MCP-injected memory blocks arrive (mem0 `kind=fact` or `kind=insight`):

1. **Identify source layer** — mem0 (`:18791`), CLAUDE.md (this file), or L0 working context.
2. **Check trust tier** — mem0 `metadata.tier` ∈ {`evidence`, `stable`, `canonical`, `insight`, `temporal`}. Treat `tier=canonical` as ground truth; `tier=insight` as synthesized higher-order facts (also high-trust, written only by the authority's nightly dream, actor `dream-consolidator`; its gated canonical promotions carry actor `dream-autopromote`; **MCP sessions cannot create or move insight records**: `memory_add` with `tier=insight` is always downgraded to `evidence`, and `memory_promote`/`memory_demote` cannot move an insight in either direction); `tier=stable` as evidence promoted after review (settled background context, passable trust; not cryptographically locked); `tier=evidence` as advisory pending confirmation. `tier=temporal` is a **tag**, not a validity-window schema (audit finding 2026-06-08: there is no `valid_from`/`valid_to` validity-window schema, and an `expires_at` cannot be set on add, the server strips it; queries on temporal must read the memory text for date ranges). The one lifecycle field that does exist is `superseded_by`: it hides a stale record from default searches and is written only through `mcp__mem0__memory_supersede`, never by hand (see "Correcting a fact" below).
3. **Cross-check on consequential claims** — for architecture decisions, deploys, credentials, or brand directives, query mem0 `tier=canonical` before asserting.
4. **Mention provenance briefly** in the plan when acting on memory ("per mem0 tier=canonical id X").

When the user explicitly says "remember this", "lock that in", "save what we learned" or equivalent:

1. Call `mcp__mem0__memory_add` with the relevant fact and `metadata={tier: "evidence", source: "user-direct"}`. Capture the returned `id`.
2. Optionally call `mcp__mem0__memory_promote(memory_id=<id>, tier="stable", reason="<one-sentence why>")` to mark it audited-evidence while it awaits canonization.
3. **Canonical cannot be set through MCP.** The shim's `memory_promote` rejects `tier="canonical"` outright, and the server additionally requires an HMAC-signed user-direct token + nonce headers the shim never sends. Hand the operator the id and a suggested reason so they can run the CLI (WSL):
   `bash ~/apps/mem0-scripts/mem0-canonize.sh <id> "<one-sentence why>"` — the same command on every box: on the authority it signs locally; on a replica it executes on the authority over SSH, and when the authority is unreachable it queues a `canonize` Outbox op (printed as `QUEUED_OFFLINE key=…`) that replays with a token minted on the authority; the session-start line reports queued/drained counts until each request has its per-fact confirmation.

Server enforcement (the audit-trail boundary added 2026-06-08 to prevent silent canonicalization): a canonical promotion requires `actor="user-direct"` plus a non-empty `reason` PLUS a valid HMAC format-2 token (`<ts>|<nonce>|promote|<mid>|<reason>`, sent as the `X-User-Direct-Token`/`X-User-Direct-Ts`/`X-User-Direct-Nonce` headers) — `mem0-canonize.sh` is the only shipped producer of that token. (A server-side allowlist also admits the dream consolidator's gated autopromote actor.) MCP promotions always carry `actor="claude-autonomous"` and can only set tier to `stable`, `temporal`, or back to `evidence` (`insight` is reserved for the dream on the authority: its consolidator label counts only with the authority's service key, which no MCP session holds, so an MCP session can neither create an insight record nor move one; moving one out of the tier takes the operator's signed `mem0-canonize.sh --action demote`). Do NOT batch canonization requests — surface each id inline so the user can run the CLI and gets per-fact confirmation.

When you notice durable facts during a session (decisions made, identity, preferences, system state changes, paths/IDs/credentials), proactively call `mcp__mem0__memory_add` with `tier: "evidence"` and a descriptive `source` field. The L1a hook-fired extractor (Codex CLI) provides a backstop, but inline capture during the live session is higher quality.

**Correcting a fact.** When a stored fact turns out to be out of date (the operator corrects it, or you see the change yourself):

1. `mcp__mem0__memory_get_by_id` both records (the old one and the newer one, if it exists) so you act on the right ids.
2. A whole fact was replaced: `mcp__mem0__memory_add` the new fact (`tier: "evidence"`, a descriptive `source`), then `mcp__mem0__memory_supersede(memory_id=<old id>, superseded_by=<new id>)`. The old record drops out of default searches and recall; `query_class="history"` still returns it.
3. One claim in a record is stale and the rest still stands: `mcp__mem0__memory_supersede(memory_id=<old id>, superseded_by=<new id>, scope="partial", detail="<which claim is out of date>")`, and `mcp__mem0__memory_update` the text too if it must change. A partial note never hides the record.
4. Never append "SUPERSEDED ..." text to a record with `memory_update` (the search filter reads the `superseded_by` field, not the text, so the stale record would stay in every search; the tool answers with a `supersede_note` when it sees such a marker). A wrong supersession is undone with `mcp__mem0__memory_unsupersede`.
5. `tier=canonical` and `tier=insight` records cannot be superseded over MCP: the server refuses them. Hand the operator the id and the correction so they can run the signed path (`mem0-canonize.sh --action demote <id> "<reason>"` first, then supersede).

Scoped to MCP-injected memory blocks only. Standard "verify, then assert" rules still apply for non-memory facts.
